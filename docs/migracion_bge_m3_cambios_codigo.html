Por qué separar EMBEDDING_MODEL de RERANK_MODEL

Hoy RERANK_MODEL se usa para DOS cosas: generar embeddings de indexación Y para reranking. Son conceptos distintos. Separar la variable permite en el futuro usar un modelo ligero para rerank (ej: cross-encoder) y bge-m3 solo para embeddings. También facilita A/B testing.

2.2.2 Embedding function (líneas 371-390)

# rag_service.py — _MultilingualEF
# ANTES:
class _MultilingualEF:
    def name(self) -> str:
        return "multilingual-minilm"
    def _encode(self, input: List[str]) -> List[List[float]]:
        if _st_model is None:
            raise RuntimeError("Modelo de embeddings no disponible")
        return _st_model.encode(input, convert_to_numpy=True).tolist()

# DESPUÉS: batch_size explícito para controlar RAM en indexación
class _EmbeddingFunction:
    """ChromaDB embedding function wrapper. Funciona con cualquier SentenceTransformer."""

    def __init__(self, batch_size: int = 64):
        self._batch_size = batch_size

    def name(self) -> str:
        return EMBEDDING_MODEL.split("/")[-1]

    def _encode(self, input: List[str]) -> List[List[float]]:
        if _st_model is None:
            raise RuntimeError("Modelo de embeddings no disponible")
        return _st_model.encode(
            input,
            convert_to_numpy=True,
            batch_size=self._batch_size,
            show_progress_bar=len(input) > 100,
        ).tolist()

    def __call__(self, input): return self._encode(input)
    def embed_documents(self, input): return self._encode(input)
    def embed_query(self, input): return self._encode(input)

Por qué batch_size explícito

bge-m3 usa ~2.5 GB de RAM base. Con batch_size grande, cada batch consume RAM adicional proporcional a batch_size × max_seq_length × hidden_dim. Con batch_size=64 y 8192 tokens, el pico de RAM se mantiene bajo control (~4 GB total). MiniLM con 128 tokens no tenía este problema.

# - Pero chunks demasiado grandes diluyen la señal específica
# - 1400 chars ≈ 250-300 tokens español → bien dentro de 8192 tokens
# - El overlap mayor (250) preserva mejor continuidad entre chunks

Impacto en memoria validada

La colección reglamentos_memoria_validada se borra y recrea vacía al detectar el mismatch de ef_version. Las respuestas aprobadas siguen en SQL Server (dbo.ConocimientoValidado), pero hay que re-inyectarlas en ChromaDB con el nuevo embedding. Si aún no hay datos validados, el impacto es cero.

El problema de MiniLM a escala

Con 384 dimensiones, al añadir documentos de PRL, RRHH, etc., los embeddings de dominios diferentes se «apelotonan» en el espacio vectorial: «riesgo eléctrico» (PRL) queda cerca de «riesgo de contacto» (REBT) porque MiniLM no tiene capacidad para separar matices técnicos en español. bge-m3 con 1024 dimensiones tiene ~2.7× más «espacio» para separar conceptos — fundamental cuando hay múltiples departamentos.

4.2 Más usuarios concurrentes

Escenario MiniLM bge-m3
1-5 usuarios simultáneos OK ~25 ms/query OK ~100 ms/query
10-20 simultáneos OK Monitor ~2.5 GB RAM compartidos
50+ simultáneos LLM es cuello LLM es cuello

En todos los escenarios realistas, el LLM domina la latencia (10s vs 0.1s del embedding). El modelo de embedding se carga UNA vez en RAM y se comparte entre requests. Con 50+ usuarios, el cuello de botella es la API de OpenAI, no el embedding local.

4.3 Más preguntas recurrentes (memoria validada)

Aspecto Impacto
MEMORY_MAX_DISTANCE = 0.35 bge-m3 produce distancias en escala diferente a MiniLM. Habrá que recalibrar este umbral tras migrar. Las distancias de bge-m3 suelen ser menores para matches buenos → puede que 0.25-0.30 sea mejor.
Precisión de match Con 1024d, «¿Qué sección tiene el cable de alumbrado?» y «¿Cuál es la sección del cableado de iluminación?» tendrán distancia más baja → menos duplicados en memoria, mejor reutilización.
Escala de memoria 1000 respuestas validadas × 1024d = ~4 MB en ChromaDB. Sin problema. Con MiniLM sería ~1.5 MB. Ambos negligibles.

7. Plan de ejecución

Fase 1 — Cambio de modelo ~30 min

Cambiar EMBEDDING_MODEL en config.py, adaptar _EmbeddingFunction, actualizar _EF_VERSION y _MEMORY_EF_VERSION. Ejecutar reset_documents() + sync_documents().

Fase 2 — Validación con queries reales ~1 hora

Probar las queries problemáticas conocidas: electrificación básica, distancia 0.2m, generadoras BT-40, secciones de conductores. Comparar distancias top-10 antes/después. Recalibrar MEMORY_MAX_DISTANCE.

Fase 3 — Ajustar chunk size (opcional) ~1 hora

Subir CHUNK_SIZE a 1400-1500. Reindexar. Comparar de nuevo. Esto reduce número de chunks (~3000 vs 3848) y mejora señal por chunk.

Fase 4 — Simplificar scoring Futuro

Si Fases 1-3 muestran mejora consistente: desactivar boosts de dominio uno a uno y medir impacto. Eliminar table_collection queries. Evaluar si reranking sigue siendo necesario.

Fase 5 — Sparse retrieval Futuro lejano

Explorar embeddings sparse de bge-m3 para reemplazar scoring léxico manual. Requiere almacenar sparse vectors (ChromaDB no soporta nativamente → evaluar Qdrant o índice invertido custom).

Resumen ejecutivo

Cambios mínimos: ~30 líneas entre 3 archivos (config.py, rag_service.py, memory_service.py).

Lo que se conserva: TODO el scoring híbrido, domain routing, enriquecimiento de tablas, context prefix, noise filter, OCR, cache, tests. El cambio es aditivo, no destructivo.

Impacto en escalado: bge-m3 con 1024 dimensiones escala mucho mejor a múltiples departamentos. 384d de MiniLM no tiene espacio vectorial suficiente para separar REBT + PRL + RRHH + RITE sin scoring agresivo por dominio. Con bge-m3, añadir un nuevo departamento = añadir PDFs y reindexar, sin tocar código.

Coste real: ~2 GB más de RAM y ~80 ms más por query. En un pipeline donde el LLM tarda 10 segundos, es invisible.

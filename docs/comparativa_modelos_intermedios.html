ChatBot RAG — Regenera Energy — Mayo 2026
MiniLM (actual) vs alternativas CPU · Referencia bge-m3 (GPU/Azure)

1. Contexto — Por qué buscar alternativas a bge-m3

El problema: bge-m3 es el mejor modelo disponible para este pipeline, pero en CPU Windows su inferencia es prácticamente inviable para indexar: cada batch de 64 chunks tarda 2-5 minutos, y un reindex completo puede superar 1 hora.

La causa: PyTorch CPU no tiene soporte nativo FP16 para operaciones transformer en Windows. FP32 funciona pero el modelo (568M parámetros, 24 capas) es demasiado pesado para ser útil en desarrollo local.

El objetivo: encontrar modelos que mejoren a MiniLM (especialmente en ventana de contexto > 128 tokens) manteniendo una velocidad razonable en CPU.

4. El problema de la ventana de 128 tokens (MiniLM) — solucionado en todos los candidatos

«En una electrificación básica, indícame la sección del cableado de alumbrado»
Un chunk de 900 chars en español genera ~180 tokens. MiniLM solo ve los primeros 128: trunca silenciosamente el 30-40% del texto de cada chunk.

Con e5-small, mpnet-base o e5-base (512 tokens): el chunk de 900 chars (~180 tokens) entra completo. El prefijo [ITC-BT-25] INSTALACIONES INTERIORES... y el dato C1 Iluminación — 1,5 mm² son visibles en su totalidad para el modelo.

Queries simples (1 concepto)

MiniLM: Funciona

e5-small: +10-15% mejor semántica en español

mpnet/e5-base: +15-20%

bge-m3: +20-25%

Queries multi-concepto

«electrificación básica + alumbrado + sección»

e5-small: +20-30% ventana completa

mpnet/e5-base: +30-40% + 768d

bge-m3: +35-45%

Queries con números

«distancia mínima 0,2 m»

e5-small: mejora moderada (384d)

mpnet/e5-base: mejor (768d captura mejor)

bge-m3: +25-35% (1024d + sparse)

Queries sobre tablas (FILA_TABLA)

Crucial para ITC-BT-25 + C1

e5-small: gran mejora prefijo ITC completo

mpnet/e5-base: mayor mejora

bge-m3: máxima mejora

Queries cross-ITC (BT-40)

e5-small: similar a MiniLM en 384d

bge-m3: mejor (1024d)

Escalabilidad multi-dpto.

Al añadir PRL, RRHH, RITE...

e5-small: 384d se satura como MiniLM

mpnet/e5-base: 768d escala mejor

bge-m3: 1024d escala óptimo

6. Implicaciones en Azure AI Search (cambio de dimensiones)

7. Cambios necesarios en el código

Para e5-small (mínimo — solo .env)

# .env — cambiar 2 líneas:
EMBEDDING_MODEL=intfloat/multilingual-e5-small
RERANK_MODEL=intfloat/multilingual-e5-small

# El resto del código funciona sin cambios.
# _EF_VERSION cambia automáticamente → reindex automático.
# Azure AI Search: sin cambios (384d = igual).

Para mpnet-base o e5-base (requiere actualizar dimensiones)

# .env:
EMBEDDING_MODEL=intfloat/multilingual-e5-base         # o paraphrase-multilingual-mpnet-base-v2
RERANK_MODEL=intfloat/multilingual-e5-base

# azure_rag_service.py — línea ~169: sin cambios de código
# (encode() genera el vector del tamaño que corresponde al modelo)

# LanzarChatbotNube.bat — actualizar dimensiones en schema del índice:
dimensions = 768    # era 384

Veredicto

Para desarrollo local (Windows CPU): intfloat/multilingual-e5-small es el cambio óptimo. Mismos parámetros que MiniLM (118M), misma velocidad, mismas dimensiones (384d → sin tocar Azure), pero con 512 tokens de ventana en vez de 128. Eso resuelve el truncamiento que causa el fallo en queries multi-concepto sin ningún coste adicional. Cambio en 2 líneas del .env.

Para producción Azure: BAAI/bge-m3 sigue siendo la elección correcta. El build Docker descarga el modelo una vez, la indexación inicial en Linux es viable, y la calidad de retrieval es máxima.

Estrategia recomendada: e5-small en local para desarrollo → bge-m3 en Azure para producción. El código ya soporta cambiar el modelo por variable de entorno sin tocar nada más.
